# Backend / Full-stack 과제: 상담 요청 상태 전이

Flutter 앱과 Spring Boot API가 하나의 상담 요청 흐름을 완성하는 풀스택 과제입니다. 단순 CRUD보다 상태 전이, 동시성·멱등성, 모바일 네트워크 실패 대응을 중점적으로 평가합니다.

Web·Flutter 단독 전형은 기존 `mock-api`를 사용합니다. 이 디렉터리는 Backend 또는 Full-stack 전형에만 사용합니다.

## 제공되는 것

- Spring Boot 3.5.6, Java 25, Gradle wrapper
- PostgreSQL 17 Docker Compose
- Flyway 기반 병원·카테고리 마스터 및 과제 사용자 seed 데이터
- 실행 가능한 `/health` endpoint
- 논리 ERD, 상태 정책, 앱·API 계약 문서

병원 데이터와 그 관계는 제공하지만 상담 요청 도메인의 물리 스키마는 제공하지 않습니다. 지원자는 [도메인 모델](./docs/domain-model.md)을 근거로 자신의 마이그레이션을 작성해야 합니다.

## 시작하기

```bash
docker compose up -d
./gradlew bootRun
curl http://localhost:8080/health
```

PostgreSQL은 `localhost:5433`에서 실행됩니다. Flyway는 애플리케이션 시작 시 `src/main/resources/db/migration/V1__hospital_master.sql`을 적용합니다.

초기화가 필요하면 다음 명령으로 과제용 PostgreSQL 데이터만 제거할 수 있습니다.

```bash
docker compose down -v
```

## 구현 과제

### 1. 상담 요청 도메인과 API

[도메인 모델](./docs/domain-model.md)의 상태 전이와 관계를 구현하고, [API 계약](./docs/api-contract.md)의 API를 제공합니다.

- Controller–Service–Repository 책임을 분리합니다.
- 요청 검증과 일관된 오류 응답을 제공합니다.
- `DRAFT → SUBMITTED → CANCELLED` 이외의 상태 전이는 거부합니다.
- 제출은 중복 탭·타임아웃 재시도에도 정확히 한 번만 반영됩니다.
- 상태 변경 이력을 보존합니다.
- PostgreSQL 마이그레이션과 필요한 인덱스·제약을 작성합니다.

### 2. Flutter 앱 연동

기존 Flutter 보일러플레이트의 패턴(Riverpod, Dio, 계층 분리)을 사용해 아래 경험을 구현합니다.

- 병원 목록 조회·카테고리 필터·1~3개 선택
- 상담 내용 작성, 초안 저장·수정
- 제출·취소, 요청 목록·상세 및 상태 이력 확인
- 로딩·빈 상태·오류·재시도 처리
- 중복 탭과 네트워크 타임아웃에도 앱과 서버 상태가 어긋나지 않는 처리

API base URL은 Android 에뮬레이터에서 `http://10.0.2.2:8080`, iOS 시뮬레이터에서 `http://localhost:8080`을 사용합니다.

### 3. 테스트와 문서화

- 단위 또는 통합 테스트를 3개 이상 작성합니다.
- 정상 흐름 외에 중복 제출, 잘못된 상태 전이, 병원 선택 검증 중 최소 2가지를 다룹니다.
- 제출 README에는 실행 방법, 아키텍처, 스키마/인덱스, 동시성 전략, AI 사용 범위와 검증 방법을 기록합니다.

## 선택 과제

- 커서 기반 페이지네이션
- OpenAPI 문서화와 계약 테스트

- 낙관적 락·비관적 락의 비교 및 채택 근거
